From a website to a Lens, one prompt at a time.

CyberCowboys began as a browser app with a SQLite database behind it. This log records how closed-loop agentic development turned that web app into a Spectacles game — the prompts, the files handed over as input, and what came back. The artwork — obstacle references, menu screens and every button texture — I made myself; CLAD gave it structure and behaviour.

Where it started

Before CLAD, the game was the website. I had built cybercowboys-back.fly.dev as a course designer — HTML, CSS and vanilla JavaScript on a Node backend, with SQLite holding eleven tables covering obstacles, path points, arena dimensions, calibration and the saved-course library.

The dynamics of the game were shaped as functionality of that web application first. Deciding what an obstacle is, what a path point is, and how a lesson gets saved and reloaded all happened in the relational schema before any of it existed in 3D.

To play it on Spectacles, I depended on a WebView. The Lens showed the website floating in front of the rider. It worked, but it wasn't a game — it was a web page you happened to be wearing.

The goal for CLAD: keep the database as the single source of truth, but replace the WebView with a real Lens that renders the arena as 3D objects on the floor, fed live from the same tables over a WebSocket.

The workflow

Each phase below is a prompt or short sequence of prompts, the files handed over as input, and what came out the other side.

Phase one · leaving the WebView

Render the arena as real 3D objects

The first substantial ask. The web app already knew how to describe a course; the Lens needed to draw one.

Prompt
My Lens currently shows my website in a WebView. I want the arena rendered as
real 3D objects on the floor instead.

The backend is a Node + SQLite app at cybercowboys-back.fly.dev. It already
broadcasts table snapshots over a WebSocket at wss://cybercowboys-back.fly.dev/.
The Obstacles table has a type column (cone, pole, barrel, cavaletti, stop,
start_line, finish_line, number_tag) and x/y positions in canvas pixels. The
Paths table has ordered waypoints with a colour.

Write a TypeScript component for Lens Studio that connects to that WebSocket,
subscribes to those tables, and instantiates the right prefab for every row
under an arenaRoot object. It should rebuild whenever a snapshot differs from
the last one it drew. Lens Studio world units are centimetres and the database
stores pixels, so give me one scale input that converts between them.
What came back The first version of ArenaStreamer.ts — WebSocket client, snapshot handling, and prefab instantiation keyed by obstacle type. The pixel-to-metre transform became the arenaScale input that still exists today.
ArenaStreamer.ts ArenaStreamerTyped.ts
Phase two · finding the floor

Path Pioneer, handed over as a .zip

The arena rendered, but it hung at eye level. Rather than describe floor detection, I gave the working sample as input and asked for the algorithm to be lifted out of it.

Attached
PathPioneer.zip  —  Snap's sample project, unmodified
Prompt
Attached is the Path Pioneer sample project as a .zip. It has a ground-plane
detection routine where you look at the floor and hold still until a ring
fills, and then it places content on the detected surface.

Extract that detection and adapt it for my project. When detection completes I
need it to set the world Y of my arenaRoot object to the measured floor height
and lock it there. Every obstacle is laid out at arenaRoot's local y = 0, so
local zero has to mean the real ground.

Two things it must handle that the sample doesn't:
1. In the Lens Studio editor preview there is no real depth, so it should drop
   to a plausible assumed floor immediately rather than sitting at eye level.
2. Accept only horizontal surfaces — a gaze hit on a wall should be rejected.
What came back SurfaceDetection.ts and CircleAnimation.ts adapted from the sample, plus a new FloorPlacer.ts that owns arenaRoot's world height. I later customised it, adding pinch-to-recentre so the rider can move the arena's X and Z without re-running detection.
SurfaceDetection.ts CircleAnimation.ts FloorPlacer.ts
Phase three · 3D assets

Example .zip in, working .fbx .zip out

The hardest thing to get right by description alone. The trick was giving a working import as the example, so the folder structure and supporting files came back correct rather than approximately correct.

Attached
working-fbx-example.zip   —  an asset that already imports cleanly into Lens Studio
cone.png, barrel.png, cavaletti.png, stop.png, fence.png
                          —  reference images made in Gemini and Adobe Illustrator
Prompt
The first .zip is an asset that already imports into Lens Studio without errors
— use its folder structure, its .fbm texture folder layout and its supporting
files as the template.

The images are the objects I want built: a traffic cone, a wooden barrel, a
cavaletti cross, a stop marker and a jump fence.

Give me back a .zip per object, matching the example's structure exactly, with
the .fbx and every supporting file in the right place so Lens Studio imports it
with no missing-texture warnings. Keep the pivot at the base of each object,
because they get laid on the floor at local y = 0.
What came back Importable asset bundles per object. The pivot-at-base instruction mattered more than anything else in the prompt — it's what lets every obstacle sit flat on the arena floor without per-object offsets.
traffic-cone/ barrel-nuevo/ equestrian-cavaletti/ stop-base/ finish-line-nuevo/
Phase four · the interface

Textures I made, buttons CLAD wired up

The look came first and by hand. I made the start-menu artwork and every button texture myself — some generated with Gemini and ChatGPT, others drawn and finished in Adobe Illustrator: the main logo, Start and Credits, Change Direction, Calibration, Choose Lesson, Home, Edit, Reload and the info buttons.

Because the artwork was already resolved, the prompt could be entirely about behaviour rather than appearance.

Attached
mainlogo.png · startbutton.png · creditsbutton.png · homebutton.png
changedirections.png · calibration.png · chooselesson.png · refresh.png
        —  textures made in Gemini, ChatGPT and Adobe Illustrator
Prompt
Attached are the button and menu textures I made. Build them into the Lens as
real interactive UI — I don't need any art generated, only the behaviour.

- Each button is a quad with its texture applied, sized in real-world
  centimetres so it reads the same on every pair of glasses.
- Use Spectacles Interaction Kit PinchButton so they respond to a pinch at a
  distance, not just a touch.
- Start screen shows the logo, Start and Credits. Pressing Start hides the menu
  and reveals the game; Credits swaps to the credits screen and back.
- Home is always visible and returns to the start screen from anywhere.
- The info buttons should all open ONE shared panel, with the text and image
  supplied by whichever button opened it — I don't want two panels fighting
  over state.
What came back StartMenu.ts owning the screen flow, and a small script per button rather than one monolith. The shared-panel instruction turned into InfoPanelTyped.ts plus a per-button content carrier, which is why two buttons can never race each other over the panel's state.
StartMenu.ts InfoPanelTyped.ts InfoPanelButtonTyped.ts ChangeDirectionButtonTyped.ts RegenerateCodeButtonTyped.ts StartArenaButtonTyped.ts RefreshButtonTyped.ts WebViewReload.ts
Phase five · guidance

Reading the rider, not just drawing the floor

With the arena on the ground, the Lens could start guiding the person inside it. This is where the project met the theme.

Prompt
I want the Lens to guide the rider rather than only draw the course.

A person's head dips once per stride, at the moment the heel strikes. Track the
camera's Y position, find those local minima, and use the interval between them
as cadence. Combine that with smoothed horizontal velocity to predict where the
next four footfalls will land, and drop a marker at each one.

Requirements:
- A marker under the wearer that follows them, smoothed so it doesn't copy head
  tracking jitter.
- The four predicted markers should hide below a walking speed threshold, so
  they don't pile up when someone stands still.
- Expose the bob threshold and the speed threshold as inputs so I can tune them
  on device.
What came back The step-prediction system inside ArenaStreamerTyped.ts. Both thresholds became Inspector inputs — stepBobThresholdCm and stepMinSpeedMps — which is what made it tunable in a real arena instead of only in the editor.
Phase six · customisation

Moving the logic back to the server

Change Direction started as a view flag inside the Lens. That was wrong, and fixing it is the clearest example of the loop closing — I could see the bug on device, describe it, and have the fix land on both halves of the system at once.

Prompt
Change Direction currently flips a private flag inside the Lens, and it's
mirroring about the rider instead of about the course's own centre line. So the
glasses and the website disagree — anything placed off-centre jumps across the
arena in AR and stays put on the web.

Move it to the server. The button should send a message; the server rewrites the
obstacle and path rows reflected about the layout's centre line, recomputes the
calibrated columns through the normal pipeline, and broadcasts the result. It
must be its own inverse, so pressing it twice returns the original course.
What came back A server-side mirror and a thin ChangeDirectionButtonTyped.ts that just sends the request. Because the server is the single source of truth, the designer's screen and the rider's floor can no longer disagree.
Phase seven · surviving the arena

Hardening the connection

Everything here exists because arena wifi is the one part of the system nobody controls. On a good connection none of it fires.

Prompt
This runs in a riding arena on bad wifi. Make the WebSocket layer survive it:

- Coalesce snapshot requests so a burst of triggers becomes one pull.
- Exponential backoff with jitter on reconnect, capped, so a downed server isn't
  hammered every three seconds by every pair of glasses in the room.
- Abandon half-open sockets after a connect timeout and retry, instead of
  waiting forever.
- Queue requests made while the link is down in an outbox and replay them in
  order on reconnect, so a button press is never silently lost.
- Fingerprint snapshots so a rebroadcast of data already on the floor costs
  nothing.
- An optional label reporting CONNECTING / LIVE / OFFLINE.
What came back The resilience layer in the streamer. The status label mattered most in testing: on a slow network, the difference between "still loading" and "broken" is the whole of the rider's experience.

Handing over files as input

The pattern that worked repeatedly was show, don't describe. Three times the fastest route to a correct result was attaching something that already worked and asking for the same shape back.

What I attachedWhat I asked forWhy it worked
Path Pioneer .zip The floor-detection algorithm, adapted to my arenaRoot Describing gaze raycasting and surface classification in prose would have taken longer than attaching the reference implementation
A working FBX import .zip New objects in the same folder structure Lens Studio is specific about .fbm folders and supporting files; an example carries that detail implicitly
Gemini / Illustrator images 3D objects matching them An image is an unambiguous spec for shape, proportion and colour
Button & menu textures Interactive UI with pinch behaviour With the art already finished, the prompt was purely about interaction — no back-and-forth over how a button should look
The live SQLite schema A client that mirrors the server's transform exactly Both halves had to agree on pixel-to-metre conversion or the AR layout drifts from the web designer

What worked, what didn't

Attaching working examples

Every time I gave a functioning artefact as the template rather than describing the target, the result came back usable on the first or second try.

Asking for Inspector inputs

Requesting that thresholds be exposed as tunable inputs, not constants, is what made the step prediction adjustable on device instead of only in the editor.

Naming the invariant

"The server is the single source of truth" and "local y = 0 means the ground" were worth restating in prompts. Most bugs traced back to one of them being violated.

Making the art first

Bringing finished textures to the table meant every UI prompt could be about behaviour. Nothing was spent negotiating appearance.

Describing 3D by words alone

Early attempts at obstacle assets from text descriptions produced things that imported with missing textures or wrong pivots. Images and an example .zip fixed both.

Letting logic live in the Lens

Change Direction as a client-side flag felt simpler and was wrong. Anything that changes the course has to happen where both clients can see it.

Trusting the editor preview

Floor detection behaves differently with no real depth data. The assumed-floor fallback exists because of the gap between preview and device.
